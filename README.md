# CinemaLog — TDD demonstration

Учебная реализация требований к приложению «CinemaLog», подготовленная как демонстрационный проект по Test-Driven Development.

## Стек

- Java 21
- Swing (desktop UI; не требует отдельного UI runtime)
- SQLite через `org.xerial:sqlite-jdbc`
- JUnit 5
- Mockito
- Maven

## Запуск

```bash
mvn test
mvn package
java -jar target/cinemalog-tdd-1.0.0.jar
```

При первом запуске рядом с приложением создаётся локальный `cinemalog.db`.

## Архитектура

```text
ui
  MainFrame / RecordDialog
       |
application
  JournalService / BackupService / RecordValidator
       |
application.port
  JournalRepository / BackupStore
       |
infrastructure
  SqliteJournalRepository / JsonBackupStore
       |
SQLite / filesystem
```

Правило: application-слой не знает о SQLite, Swing и файловой системе. Это позволяет юнит-тестам проверять поведение сервиса через Mockito без сети, диска, БД или UI.

## Почему это соответствует TDD-подходу из задания

1. Поведение сначала формулируется как атомарное требование.
2. Для поведения создаётся Given–When–Then unit test.
3. Тест использует конкретные входные данные и конкретный ожидаемый результат.
4. Внешние зависимости заменены mock-объектами.
5. Реализация минимальна относительно требования.
6. После прохождения тестов код рефакторится без изменения внешнего поведения.
7. Набор тестов запускается целиком после каждого изменения.

Тесты намеренно не используют SQLite и не пересекают границы процесса: это соответствует правилу из учебной теории, что внешние зависимости превращают тест в интеграционный, а для unit-уровня используется mock/fake. 

## Основной TDD-фокус: ФТ-1.1 — ФТ-1.4

### ФТ-1.1 — создание записи
Атомарные поведения:
- валидная запись создаётся;
- запись получает идентификатор;
- дата добавления формируется автоматически;
- запись передаётся repository на сохранение;
- дубликат отклоняется до сохранения;
- подтверждённый пользователем дубликат может быть добавлен.

### ФТ-1.2 — поля формы и ограничения
`RecordValidator` проверяет каждое атомарное ограничение отдельно: обязательность, длину названия, год, рейтинг, комментарий, тип контента и обязательные данные сериала.

### ФТ-1.3 — сериал
`SeriesProgress` хранит количество сезонов, количество серий по каждому сезону и просмотренные серии; `RecordValidator` проверяет диапазоны и взаимные ограничения.

### ФТ-1.4 — обязательные поля
Ошибка представлена структурой `ValidationException.errors`, где ключ — поле формы, значение — сообщение. UI может показать ошибку рядом с соответствующим полем, не закрывая форму.

## Другие реализованные требования

- CRUD записей;
- четыре статуса;
- смена статуса из списка;
- предложение оценки при переходе в «Просмотрено»;
- сброс оценки при уходе из «Просмотрено» после подтверждения;
- оценка только 1–10 и только для просмотренных;
- заметка с автосохранением при потере фокуса и закрытии;
- прогресс сериала и `+1 серия` с ограничением;
- фильтры типа, жанра, года, наличия оценки;
- поиск от двух символов без учёта регистра;
- сортировка по названию, году, оценке и дате добавления;
- статистика;
- резервное копирование `.clbackup` и восстановление с подтверждением;
- локальная SQLite без интернет-зависимости;
- русскоязычный интерфейс.

## Где смотреть тесты

`src/test/java/ru/cinemalog/application/`

- `RecordValidatorTest` — атомарная валидация требований ФТ-1.2/1.3/1.4.
- `JournalServiceTest` — поведение журнала, CRUD, статусы, оценка, прогресс, поиск, фильтры и статистика.
- `BackupServiceTest` — поведение backup/restore через mock `BackupStore`.

Интеграционные тесты сознательно не включены в набор сдаваемых тестов: задача требует именно изолированных unit-тестов.
